1. 系统的物理防线：Runtime Invariants

在许多异步系统中，状态撕裂（State Inconsistency）往往是隐蔽的：它不会当场报错，而是在运行若干轮后导致模型产生幻觉，或者导致后续保存的文件损坏。

Harness 的断言哲学：
“只在两个独立的观测系统可能发生隐蔽分歧时，编写 Invariant；且一旦分歧，立刻 Fail Loud。”
在 packages/core/agent-loop/src/invariant.ts 中，就存在这样一道守护整个系统底线的断言： 

// packages/core/agent-loop/src/invariant.ts 核心源码片段
ctx.on('llm/stream', (options: GenerateOptions, next) => {
  const session = ctx.sessions.get(options.sessionId)
  const expected = session.deriveMessages()

  // 💥 关键校验：发送给 LLM 的 messages 必须完全与从日志投射出的数据一致！
  if (JSON.stringify(options.messages) !== JSON.stringify(expected)) {
    fail(`llm request for session "${session.id}" diverges from the dispatch-time durable derivation (log-reconstruction desync)`)
  }

  return next()
}, { global: true, prepend: true })

如果你在开发插件时，图省事在某个请求拦截器里直接 options.messages.push(...)，代码会在进入 llm/stream 前一瞬间被这个 Invariant 直接熔断，并打印 log-reconstruction desync。这逼迫所有开发者必须严格遵守 “Model-Visible ⟺ Logged”。

2. 典型排错战役：3 大疑难场景与破局

场景 1：启动秒退，提示“waiting for services: [...]” Boot Failure

现象： 运行 CLI 报错退出，终端报告某个插件未能启动，提示缺少依赖服务。

排查武器： 运行配置快照打印：

pnpm dsh --profile <profile-name> --dump-config

原因与解法： 检查该插件的 inject: string[] 字段。通常是当前 profile 组合的 Bundle 缺少了对应的 Provider（例如注入了 kv，但没装配 kv-memory）。在 profile 的 cordis.patch.yml 中补上该插件配置即可。

场景 2：插件监听了事件，但下游的系统安全/压缩插件神秘失效 Waterfall Broken

现象： 自定义插件介入 agent/pre-step 后，原有的 compaction-basic（自动压缩）不再工作，上下文无限膨胀直至溢出。

原因与解法： 编写 Cordis Waterfall 监听器时违反了委托协议：

// ❌ 错误写法：直接 return，掐断了后面的链条！
ctx.on('agent/pre-step', async (agent, messages, next) => {
  return { kind: 'enter', messages }
})

// ✅ 正确写法：必须调用 await next() 传递控制权并解构传递！
ctx.on('agent/pre-step', async (agent, messages, next) => {
  const decision = await next(agent, messages)
  return { ...decision, messages }
})
场景 3：热重载或 Session 结束后，产生“幽灵事件”（Ghost Events） Resource Leak

现象： 客户端已经关闭了对话，但控制台依然定期打印某些轮询日志或心跳包。

原因与解法： 注册副作用时没有使用 ctx.effect() 绑定生命周期：

// ❌ 错误写法：裸调用 setInterval，Session 销毁时定时器依然在跑
setInterval(() => pollStatus(), 1000)

// ✅ 正确写法：将销毁逻辑作为 Disposer 返回给 Cordis
ctx.effect(() => {
  const timer = setInterval(() => pollStatus(), 1000)
  return () => clearInterval(timer)
})

3. 零成本复现神器：Snapshot Replay 测试

调试 Agent 系统最头疼的就是复现 Bug：因为模型输出具有随机性，而且调大模型 API 又慢又花钱。

Harness 的秘密武器：

得益于纯函数 deriveMessages() 和不可变的 Session Log，Harness 维护了一套庞大的录制会话库（在 snapshots/ 目录）。
你可以在完全没有配置 DEEPSEEK_API_KEY 的离线环境下，用毫秒级速度重放一个长达数十轮的复杂会话： 

pnpm run test:snapshot -t <snapshot-test-name>

这是验证你的插件修改是否破坏核心时序或事件回放的最高效手段！

挑战排错实战题：

问题 1：当系统抛出 `log-reconstruction desync` 异常时，最精准的排查方向是？
A. 检查网络连接是否超时，或者 LLM API 是否返回了 502 错误
B. 检查是否有代码在内存中擅自篡改了待发送的 messages，而未通过 Session Event 正规记录
C. 检查 SQLite 数据库文件是否有写入锁冲突导致落盘延迟
问题 2：为什么我们在开发 dsh 插件时，所有对外部资源的监听（如事件、定时器、子进程）都必须包裹在 `ctx.effect()` 里？
A. 只是为了让 TypeScript 能够推导返回值的类型
B. 可以让定时器在多核 CPU 之间并行加速执行
C. 保证在插件卸载、热重载或 Session 销毁时，副作用能够自动被逆向清理，防止悬挂引用和幽灵回调
