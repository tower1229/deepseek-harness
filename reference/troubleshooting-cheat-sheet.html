🚨 5 大高频故障模式与应对策略

故障现象 / 报错信息 根本原因 排查定位手段 修复方案
log-reconstruction desync 违反了 Model-Visible ⟺ Logged。模型看到的 messages 与 session.deriveMessages() 不一致。 检查是否有插件在 agent/request 中强行修改 options.messages 而未写入 Session Event。 必须先通过 session.append() 记录领域事件，再通过投影由纯函数生成消息。
Plugin Hang / Service Missing 插件声明了 inject: ['foo']，但当前 Profile/Bundle 中未装载提供 foo 的插件。 运行 pnpm dsh --profile <name> --dump-config 查看生效插件列表。 在 Profile 中补齐缺失 Bundle，或在 cordis.patch.yml 中配置引入对应 Provider。
Waterfall Short-circuit 事件监听器没有调用 await next(...)，导致后续插件（安全审查、压缩、指令重写）全部被吞。 断点定位 agent/pre-step 或 agent/request 监听器执行流程。 严格按照 const res = await next(...); return { ...res, ... } 规范向下委托。
Zombie Handler / Leak 插件在装载时注册了事件或定时器，但没有通过 ctx.effect() 暴露 Disposer。 在热重载（Live Reload）或 Session 销毁后观察是否依然收到已销毁会话的事件。 所有副作用必须包裹在 ctx.effect(() => { return () => cleanup() }) 中。
Tool Timeout / Lockup 工具在 execute 中没有监听或传递 exec.signal，或者独占工具耗尽时间阻断排空。 观察控制台是否超时退出，检查异步 IO（fetch/spawn）是否携带 signal。 将 exec.signal 传入底层 IO，或在长耗时循环中定期检查 exec.signal.aborted。

🛠️ 必备排查诊断命令

  • pnpm dsh --profile <name> --dump-config
    查看配置层叠最终结果与插件挂载树。
  • pnpm run test:snapshot -t <name>
    在本地零 Key、零网络依赖下重放会话事件流，定位回归问题。
  • pnpm run typecheck
    严格模式检查 Context 声明合并与类型安全。
  • pnpm run hygiene
    检查 package.json 依赖完整性与 publint 规范。

🛡️ Invariants 架构原则

  • 独立观察防分歧：只在两个系统独立观测点可能产生隐蔽分歧时编写 Invariant（如内存派发 vs 磁盘事件流）。
  • 拒绝静默吞错：fail() 立即中断，不允许为了容错而 fallback 隐藏架构设计漏洞。
  • Fail Loud, Fail Early：启动期的配置错误绝不留到运行期；运行期的状态撕裂绝不留到下个 Step。
