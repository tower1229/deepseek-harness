Lesson 0002 · Core Runtime

Agent Loop 运行时机制：Turn、Step 与 Session Log 状态投影

解密无特权 Agent 驱动器、事件溯源日志设计，以及 Model-Visible ⟺ Logged 铁律

前置要求 Lesson 0001 (Cordis 插件树)
预期用时 10 - 12 分钟
核心交付物 掌握消息消费流水线与工具调用调度模型

1. 破除直觉：为什么内存中没有 messages 数组？

在大多数简单 Agent 框架中，通常是这么写的： 

// ❌ 传统框架常见做法：内存直推数组
const messages = []
messages.push({ role: 'user', content: prompt })
const response = await llm.chat(messages)
messages.push(response)

这种做法在复杂系统中有致命缺陷：无法做严格的确定性回放（Replay）、无法在不破坏历史的前提下平滑压缩上下文、多插件协同状态不可追溯。

DeepSeek Harness 核心公理：Model-Visible ⟺ Logged（所见必所记）
在 Harness 中，不存在独立常驻的 messages 数组。会话持久化日志（SessionEvent Log）是唯一的绝对真理源。模型每次调用所看到的 Message[] 历史，全部由纯函数 session.deriveMessages() 从追加日志（Append-only log）中投影重构得出！

2. Turn 与 Step 的精妙生命周期

许多初学者会混淆 Turn 和 Step。在 Harness（代码位于 packages/core/agent-loop）中，两者的界限极度严谨：

Turn（一轮完整的用户目标响应周期）

从 Inbox 原子认领：1 条排队的 User Prompt + 待办的 Next-step Input 开始，直至模型不需要调用工具且没有新的未处理输入时关闭。

Step 1: 用户输入 → 模型决定调用工具 step/start → step/end
agent/pre-step 判定 → user/message 落盘 → deriveMessages() 投影 → llm/stream 流式调用 → assistant/message → tool/call → tool/result
Step 2: 消费工具输出 → 模型输出最终文本回复 step/start → step/end
认领步间 next-step input → deriveMessages() 包含刚执行的 tool_result → llm/stream → assistant/message (无更多 tool_call)

Inbox 的消费法则

  • Turn 开始点：原子认领当前挂起的 next-step input 加上 恰好一条 排队的 queued prompt。
  • Step 之间：绝对不会 认领排队的用户 Prompt，只认领工具执行或外部插件通过 agent.inject() 注入的 next-step input。这保证了一个复杂任务的完整执行链不会被半路插队的外部指令所打乱。

3. 关键拦截点：agent/pre-step (Waterfall)

当消息被认领后、step/start 写入之前，Driver 会触发 agent/pre-step Waterfall 监听链。 

// 编写拦截插件时的关键规范
ctx.on('agent/pre-step', async (agent, messages, next) => {
  // 1. 如果需要安全审查拦截：
  if (isViolatingPolicy(messages)) {
    return { kind: 'reject' } // 拒绝进入！Turn 直接关闭，不产生 Step
  }

  // 2. 正常透传或消息重写：必须调用 next() 并解构保留已有属性！
  const decision = await next(agent, messages)
  return { ...decision, messages: rewriteMessages(decision.messages) }
})

Waterfall 铁律：

Cordis Waterfall 监听器如果直接 return 而不调用 next()，会导致后续监听器被短路截断。因此在实现插件时，务必调用 await next(...)。

4. 工具调度：Parallel 并发池与 Exclusive 屏障

当大模型一次性返回多个 tool_call（例如同时搜索 3 个文件并修改 1 个文件）时，Harness 的调度器并不是简单地 Promise.all()。

  • executionMode: 'parallel'：对于只读、幂等的工具（如 read_file、grep），进入有限滚动并发池执行，并发数量受 maxParallelToolCalls 约束（默认 10）。
  • executionMode: 'exclusive'：对于写文件（write_file）或命令执行（bash），被标记为互斥独占工具。它们是顺序执行屏障（Barrier），必须等待前面所有并发工具完全执行结束并落盘后，才单独串行执行。
  • 严格模型保序（Model-Ordered）：无论并行工具由于网络或 IO 差异哪个先完成，写入持久化日志 tool/result 以及向 UI 呈现的顺序，严格按照模型最初输出的声明顺序提交。这杜绝了并发时序抖动导致的 Replay 失败。

5. 课后即时自测

检验你对 Agent Loop 核心心智模型的掌握：

问题 1：假设当前 Agent 正在执行 Step 1 的工具调用，用户通过 CLI 再次输入了一条新提示词并进入了 Inbox，此时 Driver 会如何反应？
A. 立刻抛弃当前 Step，抢占式优先执行用户的新提示词
B. 在 Step 1 结束时，把这条提示词合并进 Step 2 的模型上下文中一起发送
C. 继续执行当前 Turn 直到所有工具执行且模型回答完毕；新提示词将在下一个 Turn 开启时被认领
问题 2：为什么 Harness 规定“模型可见的任何内容都必须先成为持久化会话事件（Model-Visible ⟺ Logged）”？
A. 主要是为了给数据库或 ElasticSearch 留一份审计日志
B. 保证状态无歧义：模型上下文完全由日志纯函数推导，使得零 Key 回放测试、会话 Fork 与精准上下文压缩成为可能
C. 因为 Node.js 内存容易发生垃圾回收泄漏，存到磁盘更节省内存
